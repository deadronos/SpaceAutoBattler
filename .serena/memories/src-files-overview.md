
**Memory name:** src-files-overview

This memory summarizes the repository's `src/` directory and key patterns so future agents and contributors can quickly understand the code layout and major responsibilities.

## Top-level entry points
- `src/main.ts` — Primary application entry. Initializes app logic, sets up renderer and simulation loop, and wires UI.
- `src/simWorker.ts` — Simulation worker entry; runs physics and game simulation in a worker context (Web Worker / worker thread) and communicates with main thread.
- `src/ui.html` — Small UI wrapper used in demos/tests.

## Configuration modules
Located under `src/config/`.
- `behaviorConfig.ts` — Config for AI/behavior parameters.
- `cameraConfig.ts` — Camera settings and defaults.
- `carrierSpawnConfig.ts` — Carrier spawn parameters.
- `entitiesConfig.ts` — Definitions of entities and their base properties.
- `fleetConfig.ts` — Fleet composition and defaults.
- `gameConfig.ts` — High-level game settings (map, pacing, win/loss conditions).
- `physicsConfig.ts` — Physics constants and tuning.
- `progression.ts` — Leveling/progression rules.
- `rendererConfig.ts`, `rendererEffectsConfig.ts` — Renderer options and post-processing effects config.
- `shipVisualConfig.ts` — Visual settings for ships.
- `simConfig.ts` — Simulation-specific runtime configuration.

Notes:
- Config modules export strongly-typed objects used throughout the codebase.
- They are the primary location for tuning gameplay and visual parameters.

## Agent and AI
- `src/agent/` — Contains agent logic and utilities.
  - `lockUtils.ts` — Locking utilities used by agents to coordinate access to shared state or resources in simulation.

## Core game systems
- `src/core/` — Core gameplay systems. Contains state management, game loop abstractions, and canonical GameState representation. (Files not fully enumerated here; memory can be extended with per-file details later.)

## Rendering
- `src/renderer/` — Rendering pipeline and WebGL/three.js based renderers. Responsible for scene composition, instanced rendering, and post-processing. Refer to docs `docs/INSTANCED_RENDERING_PLAN.md` for architecture rationale.

## Utilities and types
- `src/utils/` — Common utilities used across modules (math helpers, random, serialisation, etc.).
- `src/types/` — TypeScript types and shared interfaces for GameState, Entities, Messages, and Renderer contracts.

## Build, test, and tooling
- `package.json` and `scripts/` coordinate build; `build.mjs` and `build-standalone.mjs` build bundles used for demos and tests.
- Tests live under `test/` with Playwright and Vitest setups (`playwright/`, `vitest/`).
- Linting/TS config present (`tsconfig.json`, `eslint.config.ts`, `vitest.config.js`).

## Important patterns and conventions
- Canonical GameState object used as the single source of truth for simulation and rendering.
- Simulation runs in `simWorker.ts` and communicates via message passing with main thread renderer.
- Config objects are the preferred place for tuning; avoid hard-coded constants.
- Code favors small, focused modules with clear responsibilities.
